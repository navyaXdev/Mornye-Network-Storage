How to Deploy Mornye Network Storage Using Rootless Docker Compose

Author: NavyaXdev • Topic: Hardened Containerization • Read Time: 10 min

Containerizing network storage applications introduces significant architectural challenges. Many off-the-shelf container images run their inner processes as root (UID: 0), share root filesystem namespaces with the host, and rely on sweeping permission modifications (such as chmod 777) to bypass permission errors. If a remote exploit or path traversal vulnerability affects such a container, the attacker immediately gains root-level access over the host system.

Mornye Network Storage enforces a strict rootless container model. The container executes under an unprivileged user (UID: 1000, GID: 1000), drops all Linux capabilities, and isolates storage mounts using POSIX permissions. In this comprehensive guide, we examine the production Docker architecture, volume mapping strategies, host port isolation, and automated container healthchecks.

1. The Rootless Security Architecture

Mornye implements multi-stage Docker builds based on a lean Python Alpine/Debian base. The container security posture includes:

  • Explicit Non-Root User: Inside the container, user mornye is assigned UID 1000 and GID 1000. No operations run as UID 0 after image compilation.
  • Capability Dropping (cap_drop: ALL): Prevents the container process from performing administrative operations such as altering network interfaces, loading kernel modules, or modifying raw block devices.
  • No New Privileges (security_opt: no-new-privileges:true): Blocks setuid binaries within the container from escalating permissions.
  • Read-Only Root Filesystem Compatibility: State and data are strictly directed into mounted host volumes (/data, /storage, /logs), ensuring the container root remains stateless and immutable.

2. Production Compose File (`compose.yaml`)

Here is the canonical, production-tested compose.yaml utilized by Mornye:

services:
  mornye-webdav:
    build:
      context: .
      dockerfile: Dockerfile
    image: mornye-webdav:latest
    container_name: mornye-webdav
    restart: unless-stopped
    user: "1000:1000"
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
    ports:
      - "127.0.0.1:${MORNYE_HOST_PORT:-8001}:8000"
    volumes:
      - ./database:/data
      - ./storage:/storage
      - ./logs:/logs
    environment:
      - MORNYE_PORT=8000
      - MORNYE_STORAGE_ROOT=/storage
      - MORNYE_DB_PATH=/data/mornye.db
      - MORNYE_LOG_PATH=/logs/mornye.log
      - MORNYE_AUTH_ENABLED=${MORNYE_AUTH_ENABLED:-true}
      - MORNYE_AUTH_USER=${MORNYE_AUTH_USER:-admin}
      - MORNYE_AUTH_HASH=${MORNYE_AUTH_HASH}
    healthcheck:
      test: ["CMD", "curl", "-f", "http://127.0.0.1:8000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s

3. Host Directory Permissions & The UID 1000 Rule

Because the container process runs with UID 1000, the mounted host directories must be writable by UID 1000. If the host directories are owned by root (UID 0), the container's entrypoint will fail with:

mkdir: cannot create directory '/data': Permission denied

To ensure robust operation, set ownership and permissions on the host directories prior to starting the container:

# Ensure persistent directories exist
mkdir -p database storage logs backups config

# Assign ownership to UID:GID 1000:1000
sudo chown -R 1000:1000 database storage logs backups config

# Secure permissions to user-only access
chmod 700 database storage logs backups config
Automatic Permission Repair:

If permissions ever drift, run ./mornye.sh doctor --fix. Mornye's diagnostic engine automatically identifies permission mismatches and applies correct ownership without touching unrelated directories.

4. Managing Environment Variables (`.env`)

Mornye reads its configuration dynamically from a secure .env file in the repository root. Generate your configuration from the audited template:

cp .env.example .env
chmod 600 .env

Key environment parameters include:

  • MORNYE_HOST_PORT=8001: The host port bound to loopback 127.0.0.1. Mapped to container port 8000.
  • MORNYE_AUTH_ENABLED=true: Enforces HTTP Basic Auth over WebDAV requests.
  • MORNYE_AUTH_USER=admin: Configured WebDAV administrator username.
  • MORNYE_AUTH_HASH=$argon2id$...: OWASP-compliant Argon2id password hash generated securely during setup.

5. Container Lifecycle Management

You can manage the container using standard Docker CLI commands or the unified POSIX management script ./mornye.sh:

# Build and launch containers in detached mode
docker compose up -d --build

# Verify container process status and health
docker compose ps

# Inspect live WebDAV container logs
docker compose logs -f mornye-webdav

# Execute live health probe via Mornye CLI
./mornye.sh health

# Inspect container memory, CPU, and disk usage
./mornye.sh monitor

6. Automated Backup Strategy in Docker

Because SQLite uses Write-Ahead Logging (WAL mode), creating a simple copy of mornye.db while the container is actively writing can result in a corrupt snapshot. Mornye includes an online hot-backup command that executes a consistent SQLite transaction snapshot:

# Create hot online backup snapshot
./mornye.sh backup create

# List historical snapshots with timestamps and SHA-256 hashes
./mornye.sh backup list

Summary

Deploying Mornye Network Storage via rootless Docker Compose provides an enterprise-grade private cloud storage solution that pairs operational simplicity with defense-in-depth security. Your storage remains isolated, resilient, and completely under your control.
