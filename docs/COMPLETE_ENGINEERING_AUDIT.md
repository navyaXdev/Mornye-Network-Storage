## 1. EXECUTIVE SUMMARY & AUDIT SCOPE

Mornye Network Storage is a production-grade, containerized RFC 4918 WebDAV infrastructure featuring automated cross-distribution deployment, Zero-Trust WAN access via Cloudflare Tunnels, and integrated health monitoring.

This exhaustive engineering audit was initiated following runtime discrepancies reported on modern Linux distributions (notably Debian 13 "Trixie" testing environments) and multi-tenant systems hosting pre-existing services (such as SONG Bridge on port 8000 and legacy tunnel instances).

### 1.1 The Primary Incident: Cloudflare Credential & Directory Mount Collision
When deploying Mornye on hosts with existing Cloudflare origin certificates (`cert.pem`) but without pre-extracted JSON credentials, three distinct failure cascades were identified:
1. **Certificate vs. Credentials File Confusion:**  
   Cloudflare's `cert.pem` (an X.509 Origin/Account certificate generated by `cloudflared tunnel login`) was mistakenly treated as interchangeable with the tunnel credentials JSON file (`<UUID>.json`). Passing `cert.pem` to `cloudflared` via `--credentials-file` triggers a fatal unmarshal error:
   ```
   failed to parse credentials: json: cannot unmarshal string into Go struct field ...
   ```
2. **Docker Directory Mount Inversion:**  
   When `docker compose --profile tunnel up -d` is invoked and the host-side file `./config/credentials.json` does not exist prior to container creation, the Docker daemon automatically creates an empty directory named `credentials.json` on the host. When mapped into the container at `/etc/cloudflared/credentials.json:ro`, `cloudflared` attempts to open it as a file, resulting in the fatal operating system error:
   ```
   open /etc/cloudflared/credentials.json: not a directory
   ```
3. **Protected Service Hijacking:**  
   Commands in `scripts/cloudflare_manager.sh` and `scripts/repair_engine.sh` targeted `mornye-tunnel.service` via `systemctl stop/restart`. On systems where a host-level systemd unit named `mornye-tunnel.service` (listening on metrics port 20241) is already operating, these commands inadvertently interfered with the protected external tunnel rather than controlling the containerized Mornye tunnel instance.

## 3. DEEP DIVE: CLOUDFLARE TUNNEL LIFECYCLE AUDIT

### 3.1 Cloudflare Authentication & Cryptographic Model
Cloudflare Zero-Trust architecture utilizes three distinct security artifacts:
1. **Origin / Account Certificate (`cert.pem`):**
   - **Path:** `~/.cloudflared/cert.pem` or `/root/.cloudflared/cert.pem`.
   - **Format:** PEM-encoded X.509 certificate and private RSA key.
   - **Function:** Authorizes the machine with the Cloudflare account during tunnel creation, deletion, and token extraction.
   - **Restriction:** *Cannot* be used as a tunnel credential file or mounted to `--credentials-file`.
2. **Tunnel Credentials File (`<UUID>.json`):**
   - **Path:** `~/.cloudflared/<UUID>.json` or `config/credentials.json`.
   - **Format:** JSON object containing `AccountTag`, `TunnelSecret`, and `TunnelID`.
   - **Function:** Cryptographically authenticates the tunnel daemon (`cloudflared tunnel run`) to the Cloudflare edge.
   - **Generation:** Generated exclusively when `cloudflared tunnel create <NAME>` executes.
3. **Tunnel Token (Base64):**
   - **Format:** Base64-encoded JSON payload `{"a":"<AccountTag>","t":"<TunnelID>","s":"<TunnelSecret>"}`.
   - **Function:** Can run the tunnel directly via `cloudflared tunnel run --token <TOKEN>` without any credentials file.

### 3.2 Recovery Protocol for Missing Credentials JSON
When a user already has an existing tunnel (e.g., `mornye-storage` with UUID `463ff5f0-ead1-4e10-ba29-92b3e48abf66`) and an origin certificate (`cert.pem`), but the local JSON file was removed or resides under a different user directory (`/root` vs `/home/$USER`), Mornye must:
1. Search all standard locations (`$HOME/.cloudflared`, `/root/.cloudflared`, `/etc/cloudflared`, `/home/*/.cloudflared`).
2. If not found, execute `cloudflared tunnel token <UUID_OR_NAME>`.
3. Decode the base64 token payload into its constituent fields (`AccountTag`, `TunnelID`, `TunnelSecret`).
4. Reconstruct the valid JSON credential file at `config/credentials.json`.
5. Apply permissions `644` so the container user `nonroot` can read the file.

### 4.2 Deficiencies in Existing Installers
1. **Debian 13 (Trixie) Repository Gaps:**  
   Docker does not publish an official `trixie` repository subdirectory. Adding `https://download.docker.com/linux/debian trixie stable` results in an APT 404 error. The installer must dynamically map `trixie` to `bookworm` or prioritize distro-native `docker.io` packages.
2. **Non-Systemd Service Management (Alpine OpenRC):**  
   While `installers/common.sh` contained stubs for `openrc`, container management tools in `mornye.sh` lacked automatic fallback for environments lacking `systemd`.

## 5. PORT & SERVICE ISOLATION AUDIT

### 5.1 Host Port vs. Container Port Invariant
Mornye strictly enforces the following port hierarchy:
- **Host WebDAV Port (`MORNYE_HOST_PORT`):** Configurable in `.env`, defaults to `8001`, bound strictly to loopback (`127.0.0.1`).
- **Container WebDAV Port (`WEBDAV_PORT`):** Internal to Docker bridge network `mornye-net`, defaults to `8000`.
- **Docker Compose Mapping:** `"${MORNYE_HOST_BIND:-127.0.0.1}:${MORNYE_HOST_PORT:-8001}:8000"`.
- **Cloudflare Ingress Target:**
  - In Docker runtime mode: `http://webdav:8000` (routed via container network).
  - In Host runtime mode: `http://${MORNYE_HOST_BIND}:${MORNYE_HOST_PORT}`.

### 5.2 Protected Host Services Inventory
Under no circumstances may Mornye stop, kill, reconfigure, or probe maliciously any of the following pre-existing services:
1. **SONG Bridge:** `mornye-storage.service` (listening on host `0.0.0.0:8000`, PID 13951).
2. **Existing Cloudflare Tunnel:** `mornye-tunnel.service` (listening on metrics port 20241, PID 522213).
3. **Navidrome Music Server:** `navidrome.service` (listening on host `0.0.0.0:4533`).
4. **Quick Tunnels:** `cloudflared-quick.service` (listening on port 8088).

## 6. SELF-HEALING & AUTOMATED REPAIR AUDIT

### 6.1 Interactive Lifecycle Integration
The audit confirmed that `scripts/repair_engine.sh` provides structured, risk-rated error cards and preserves user configurations when auto-repair is declined. However:
- Pre-flight checks during `setup.sh` were not fully unified with the new compatibility layer.
- Cloudflare repair handlers in `repair_engine.sh` relied on naive string replacements for ingress target alignment, which risked YAML corruption. A YAML-aware Python helper must be used.

## 7. UNINSTALLER & RESOURCE PURGE AUDIT

The `delete.sh` script previously achieved 25/25 test passes under security audit conditions. The following guarantees are verified:
- **Mode A (Safe Uninstall):** Preserves `database/`, `storage/`, `config/`, and `backups/`. Cleans only Docker containers, images, networks, and ephemeral run files.
- **Mode B (Purge):** Requires exact interactive confirmation token `"DELETE MORNYE DATA"`. Creates a timestamped `.tar.gz` safety archive before deleting user data.
- **Isolation:** Never touches foreign containers, volumes, or services lacking the `com.docker.compose.project=mornye` label.

## 8. ACTIONABLE REMEDIATION ROADMAP

Based on this audit, the remediation plan defines five engineering work packages:
1. **Centralized System Compatibility Engine (`scripts/lib/compat.sh`):** Consolidate all OS detection, package managers, and init abstractions.
2. **Centralized Port & Network Manager (`scripts/lib/port_manager.sh`):** Manage port reservations, conflict resolution, and endpoint validation.
3. **Cloudflare Tunnel Manager Redesign (`scripts/cloudflare_manager.sh`):** Implement token extraction, prevent `cert.pem` misuse, enforce container permission boundaries, and protect host tunnels.
4. **Interactive Lifecycle & Preflight Integration:** Wire `repair_engine.sh` and `compat.sh` into `setup.sh`, `mornye.sh`, and `doctor.sh`.
5. **Debian 13 Second-System Regression Test Suite:** Implement automated simulation testing for the exact multi-service scenario.
